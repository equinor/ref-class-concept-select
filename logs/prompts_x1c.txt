[context: the nature of the work]

This work builds methodology to analyze petroleum field
development projects along the lines of which decisions that
were taken at different points in time and at different
project stages. The methodology will be built by analyzing
the data from the real openly available Volve field
downloaded from databricks.

The analysis will identify different core decisions that
were made during the project, which information was
available at the time of decision, e.g., volumetric and cost
estimates, which assumptions that underlie the different
decisions, and any inconsistencies that may be found.

The methodology then works to structure some of these
decisions using a decision analysis procedure, i.e., a
decision model, e.g., a decision tree and/or influence
diagram is created using specific decision, uncertainties
and corresponding values and probabilites acquired from the
data. (Data in this sense is information directly read from
documentation and/or derived from artifacts created by the
field development team, e.g., the reservoir simulation
model and the plan for production and operation.)

Reference class forecasting is a general approach that is in
this context used to calibrate in-place volumetric estimates
though it can also be use to calibrate other probabilistic
assessments, i.e., use the outside view to challenge the
inside view.

[context: repo startup]

This repo sets up work to be conducted by a set of agents
which concentrate on performing different tasks and serve
as experts within their respective domains.

Five domains are currently identified to each be driven by
a respective agent. Each agent works primariry within its
own folder within this repo, but has access to all data
in the repo. Additional domains may be specified at a later
time.

[The agents folders and the agent specifications are:]

agents/doc: agent that analyses and extracts data from
documents that contain graphs and tables. The documents,
often given in pdfs, should be extracted to markdown and
any other format that makes both the text data and the
numerical data easy to digest by an llm agent for further
analysis. This agent also has the responsibility to create
communication artifacts, e.g., html webpages that show and
summarize the data found in the various documents. All the
the data from all the graphs (production profiles) in each
document should be exported to an excel file with the same
name as the original file.

agents/doc is also responsible for converting source docs,
e.g., .pdf and .docx files, to md format to facilitate llm
ingestion. The resulting .md file has the same file name as
the original file and is placed in a md dir in the same dir
as the original file. Moreover, cut-outs of the figures in
the document, and their corresponding tables if the figures
are plot graphs with are placed in a figs dir. Name
appropriately.

agents/sim: agent that runs reservoir simulations and/or
perform analysis on input data and output results from
reservoir simulations.

The manual for the open-source opm flow reservoir simulator
(https://opm-project.org/?page_id=955) is the reference for
the definition of the different reservoir simulator keywords
and their specification. This knowledge can serve to develop
custom simulation decks which are reduced version of the
main simulatin decks for some specific purpose
(fit-for-purpose modeling).

Equinor has a software library called resdata
(https://github.com/equinor/resdata) for reading and writing
result files from the Eclipse reservoir simulator.

agents/dmx: agent that structures decisions and is able to
create and solve decision models, e.g., influence diagrams
and/or decision trees.

agents/rcf: agent that possesses the knowledge about
reference class forecasting and has the main responsibility
for implementing this methodology when called in by other
other agents.

agents/sys: agent that has specific knowledge about how best
to organize, coordinate and integrate the different types of
data and the work created by the different agents. The other
agents can and should call in the guidelines provided by
this agent when necessary.

It ends within 0.6% of Eclipse on cumulative oil, water and gas and 0.1% on field pressure, and takes 11 minutes on 8 processes.

The changes are only what Flow stops on:

• Input errors: a surplus 13th ROCK record, a surplus 13th RSVD table, and five well records with no WCONHIST keyword are commented out. Eclipse's own log shows it ignored all three.
• Unsupported keywords: QUIESC/MOBILE and PRIORITY are removed.
• ADDZCORN: the shifts are applied in a new grid file instead (12,600 corner depths, taken from Eclipse's own output geometry).

One known difference remains uncorrected: Flow applies a TRANZ cap and a MULTZ of 0.1 in the opposite order to Eclipse, so about 1,450 cells in three tight layers have up to 10× the vertical transmissibility. A fix I tried made the run lose mass, so I left it out.

Run it with make flow-run. Details are in agents/sim/out/volve_2016_flow/README.md; pushed as 507ac5d.
